# Security hardening

Software Release Radar is designed for self-hosting. A secure deployment still depends on how the Docker host, reverse proxy, integration credentials and network access are configured.

This guide covers the expected production baseline.

## 1. Use HTTPS

For anything beyond a trusted local HTTP test, put Release Radar behind a reverse proxy with a valid TLS certificate.

Set:

```text
SESSION_COOKIE_SECURE=true
```

Then restart the stack:

```bash
docker compose up -d
```

Use HTTPS consistently. Do not enable secure-only cookies while accessing the application over plain HTTP because the browser will not send the session cookie.

## 2. Trust proxy headers only when appropriate

The safe default is:

```text
TRUST_PROXY_HEADERS=false
```

Set this to `true` only when:

- Release Radar is directly behind one trusted reverse proxy;
- the proxy sets the original address, host and scheme headers; and
- clients cannot bypass the proxy and reach the application while supplying their own forwarding headers.

If these conditions are not true, leave proxy-header trust disabled.

## 3. Restrict direct access to the application port

The default host port is `9120`.

If a reverse proxy is used, firewall or network policy should prevent unnecessary direct access to that port. The reverse proxy should be the intended entry point.

Do not expose the Docker daemon to Release Radar.

## 4. Protect `.env`

`.env` contains values that can protect sessions and decrypt stored integration credentials.

The setup helper creates it with mode `0600`.

Keep secure backups of `.env`, but do not:

- commit it to Git;
- paste it into an issue;
- include it in screenshots;
- store it in a publicly readable directory; or
- share `ENCRYPTION_KEY` separately from the deployment without a reason.

Changing `ENCRYPTION_KEY` makes previously saved encrypted integration values unreadable.

## 5. Use a strong administrator password

The setup helper requires at least 10 characters. Use a unique password generated by a password manager rather than reusing another account password.

Passwords are stored as PBKDF2-SHA256 hashes with 600,000 iterations.

The public runtime also uses SQLite-backed login throttling. Repeated failures can temporarily block further attempts for an account or source address. This is an additional control, not a replacement for a strong password.

## 6. Configure password reset carefully

Password-reset links require SMTP and use the configured application base URL.

Set **Settings → General → Application base URL** to the real HTTPS URL before relying on password reset.

Reset tokens:

- are random;
- expire after one hour;
- are single use; and
- are stored in the database as SHA-256 digests rather than plaintext tokens.

Reset requests are rate limited and return the same public response regardless of whether an account exists.

## 7. Use least-privileged GitHub access

`GITHUB_TOKEN` is optional for public repositories.

If you configure one, use the least privilege that satisfies your tracking needs. Release Radar does not need write access to tracked public repositories.

Do not use a broad personal access token simply to avoid anonymous API rate limits.

## 8. Harden Portainer access

Portainer is a management-plane integration and should be treated accordingly.

Recommended baseline:

- dedicated API token;
- least privilege available for the required inventory operations;
- internal network path where practical;
- HTTPS;
- TLS certificate verification enabled; and
- no reuse of an administrator token unless the integration genuinely requires it.

Release Radar verifies Portainer TLS certificates by default.

If you use a private certificate authority, prefer adding the CA trust to the environment rather than disabling verification permanently.

## 9. Harden SSH Docker probes

SSH probing is optional.

If enabled:

- create a dedicated SSH account or key for Release Radar;
- restrict the remote account as much as practical;
- keep only required keys in `ssh/`;
- maintain `ssh/known_hosts`;
- use strict host-key verification; and
- remove access when a tracked host is retired.

The application constructs a fixed `docker inspect` command from validated tracker fields. It is not intended as a general remote command interface.

## 10. Back up both database state and deployment secrets

Database backup:

```bash
./scripts/backup.sh
```

The backup helper uses SQLite's online backup API and validates the backup before reporting success.

Keep a protected copy of `.env` separately because the database backup does not contain `ENCRYPTION_KEY`.

Test the restore process periodically:

```bash
bash scripts/restore.sh ./backups/radar-YYYYMMDD-HHMMSS.db --confirm
```

The restore helper creates a pre-restore safety backup and attempts rollback if the requested restore fails.

## 11. Keep the image and dependencies current

Review Release Radar release notes before upgrading.

For a source checkout:

```bash
./scripts/backup.sh
git pull --ff-only
docker compose build --pull
docker compose up -d --build
```

The public repository uses CI and Dependabot to surface dependency changes. A dependency update should still pass the project tests and Docker smoke test before release.

## 12. Review outbound integrations

Depending on configuration, Release Radar can make outbound connections to:

- GitHub;
- SMTP servers;
- Pushover;
- Portainer or Dockhand;
- tracked HTTP/TCP services;
- SSH hosts; and
- an optional OpenAI-compatible API.

Only enable integrations that are needed and ensure the Docker host can reach only the networks required by your deployment policy.

## 13. Treat optional AI output as untrusted

Release notes and local deployment context can be sent to the configured AI endpoint when the assistant is used.

Do not configure an AI provider if that data should not leave your environment.

AI output is display content and advice. It should not be treated as trusted shell commands or an automatic approval to update production systems.

## 14. Monitor logs without publishing them blindly

Useful commands:

```bash
docker compose logs --tail=100 radar
docker compose logs --tail=100 scheduler
docker compose logs --tail=100 portainer-worker
```

Before sharing logs publicly, remove:

- private hostnames;
- internal addresses when they are not needed;
- email addresses;
- repository names that are private;
- tokens or credentials; and
- other identifying infrastructure details.

## 15. Report vulnerabilities privately

Do not open a public issue containing vulnerability details or proof-of-concept exploit information.

Follow [SECURITY.md](../SECURITY.md) and use GitHub private vulnerability reporting when it is available.

## Production checklist

Before exposing a deployment beyond a trusted network:

- [ ] HTTPS is working with a valid certificate.
- [ ] `SESSION_COOKIE_SECURE=true`.
- [ ] `TRUST_PROXY_HEADERS` matches the actual proxy topology.
- [ ] Direct access to the application port is restricted where practical.
- [ ] Administrator password is unique and strong.
- [ ] `.env` permissions and backups are appropriate.
- [ ] Application base URL is correct.
- [ ] Inventory-provider and GitHub credentials use least privilege.
- [ ] SSH probe keys are dedicated and `known_hosts` is maintained.
- [ ] Database and `.env` backups exist.
- [ ] A restore has been tested.
- [ ] Current CI is green for the release being deployed.

## Dockhand inventory security

Treat a Dockhand bearer token as a management-plane credential. Use a dedicated token associated with an account that can only view the required environments and containers. Keep TLS verification enabled and prefer a trusted private certificate authority over disabling verification.

A reverse proxy that serves Dockhand over HTTPS protects connections made through that HTTPS URL. It does not encrypt a direct `http://` connection from Release Radar to the Dockhand backend. Keep `ALLOW_INSECURE_INTEGRATIONS=false` when Release Radar uses the proxy URL. Set it to `true` only when deliberately accepting a trusted-network HTTP connection to the backend.

Release Radar encrypts the token in SQLite. Request errors are sanitised and do not include response bodies that could echo credentials. Application pages and JSON status routes expose only connection and job state.
